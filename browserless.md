## Overview

Browserless is far more than a scraping tool — it's a programmable rendering engine, a stealth automation platform, and a serverless browser runtime that turns Chrome into an API. Its surface area spans 10+ REST endpoints, WebSocket CDP connections, a GraphQL automation language (BrowserQL), built-in CAPTCHA solving, session persistence, live human-in-the-loop streaming, and a `/function` endpoint that lets you POST arbitrary Puppeteer code and get results back without a backend. Most teams use it for screenshots and scraping. That barely scratches the surface.

This report maps the full API surface, then presents **12 creative, non-trivial use cases** — each grounded in specific browserless capabilities that make them technically feasible.

## The Full API Surface at a Glance

Browserless v2 exposes three primary interfaces:

- **REST APIs** — stateless HTTP endpoints
- **Browser-as-a-Service (BaaS)** — persistent WebSocket/CDP connections for Puppeteer/Playwright
- **BrowserQL** — a GraphQL-based stealth automation language

All run on Chromium, Chrome, Firefox, or WebKit via Docker images.

### Core REST Endpoints

| Endpoint | Purpose |
|---|---|
| `/screenshot` | PNG/JPEG/WebP capture |
| `/pdf` | HTML-to-PDF with 20+ layout options |
| `/content` | Fully rendered HTML after JS execution |
| `/scrape` | Structured extraction via CSS selectors |
| `/performance` | Full Lighthouse audits |
| `/function` | POST raw Puppeteer code, returns anything |

| `/export` | Bundles a complete page with all resources into a self-contained archive |

### Shared Configuration Layer

Every endpoint shares a rich configuration layer: **wait strategies** (selector, timeout, custom JS function, DOM event), **request interception** (block or modify network requests mid-flight), **resource blocking** by type or URL pattern, and **launch parameters** including stealth mode, ad blocking, consent-modal blocking, residential proxy routing with geo-targeting, and custom Chrome flags.

## 12 Creative, Non-Trivial Use Cases

### 1. A Personal Wayback Machine with Visual Time-Lapse

Most people think of web archiving as saving HTML. But browserless enables something far richer: a **visual time-lapse system** that captures the rendered state of any page on a schedule, then diffs the results to surface changes humans would notice.

**How it works technically:** A cron job hits the `/screenshot` endpoint (full-page, at a fixed viewport) and `/content` endpoint for every URL in your watchlist. Store each capture with a timestamp. Run pixel-diffing (via libraries like `pixelmatch`) between consecutive screenshots to generate heatmaps of visual change. Meanwhile, diff the rendered HTML to detect structural changes — new sections, removed CTAs, altered pricing copy. The `/pdf` endpoint can simultaneously generate archival-quality PDF snapshots for legal or compliance purposes.

**The clever part:** Combine this with `/unblock` and residential proxies with geo-targeting (`&proxyCountry=de`) to capture how pages look to users in different countries. You'll see localized pricing, region-gated content, and A/B test variants that are invisible from a single IP.

### 2. Browser-as-an-Image-Processor: CSS Filters Replace ImageMagick

Use Chrome's rendering engine as an **image processing pipeline**. CSS supports blur, grayscale, sepia, hue rotation, brightness, contrast, saturate, drop-shadow, and arbitrary SVG filter chains. Canvas offers pixel-level manipulation.

**How it works technically:** POST an HTML document to the `/screenshot` endpoint where the HTML contains an `<img>` tag with your source image and CSS filters applied. Need a blurred, desaturated, cropped thumbnail at exactly 400×300? Write it in CSS, render it in Chrome, get back a PNG.

**Why this is surprisingly viable:** The `/function` endpoint takes this further — POST Puppeteer code that loads an image into a `<canvas>`, applies arbitrary pixel transformations via JavaScript, then calls `canvas.toDataURL()` and returns the result. You've just built a **serverless image processing API** with zero native dependencies.

### 3. The Meme Factory API: Dynamic Image Generation Without a Design Tool

Need to generate thousands of custom memes, certificates, event tickets, or social cards on the fly? Browserless turns HTML templates into an image-rendering API.

**How it works technically:** Build an HTML template with CSS positioning for text overlays, dynamic font sizing, and image backgrounds. POST it to `/screenshot` with the template injected as the `html` field and a fixed `clip` region matching your desired output dimensions (e.g., 1200×630 for OG images, 1080×1080 for Instagram).

**The advanced version** uses the `/function` endpoint to accept a JSON context object with all the dynamic fields, construct the HTML inside the Puppeteer script, render it, and return the screenshot. This creates a single API call that takes structured data in and returns a finished image out. You can even `import` design libraries from ESM CDNs inside the function.

### 4. Dark Pattern Detector: Auditing Manipulative UX at Scale

Consumer protection regulators and UX researchers can use browserless to **systematically detect dark patterns** across thousands of websites.

**How it works technically:** The `/function` endpoint is the key. POST a Puppeteer script that navigates to a target site, then injects a custom audit script. This script scans for known dark pattern signatures:

- Elements with `opacity` below a threshold (hidden text)
- Countdown timers that reset on page reload (fake urgency)
- Pre-checked checkboxes in forms (sneaking)
- Cookie banners where "Accept All" is a button but "Reject" is a tiny text link
- Subscription cancellation flows that require more clicks than signup

Combine this with the `/performance` endpoint's accessibility audit to flag WCAG violations that often co-occur with dark patterns. Run it across an industry's top 500 sites using **stealth mode** and **residential proxies** to see the real consumer experience.

### 5. Email Rendering Farm: Test HTML Emails Across 30 "Clients" Without Litmus

Email rendering testing is a $100M+ industry (Litmus, Email on Acid). Browserless lets you build a scrappy version in-house by injecting client-specific CSS constraints into a browser.

**How it works technically:** Take your HTML email template and POST it to `/screenshot` multiple times, each time wrapping it in a different CSS constraint set that mimics a specific email client:

| Client | Simulation |
|---|---|
| Outlook | Strip `<style>` blocks, force table-based layout |
| Gmail | Remove `<style>` tags, inline everything |
| Apple Mail dark mode | Inject `@media (prefers-color-scheme: dark)` overrides |
| Mobile (iPhone) | Viewport width 375px |
| Mobile (Android) | Viewport width 360px |

**Advanced trick:** Use `/function` to iterate through 30+ client configurations in a single browser session and return them all as a ZIP or JSON array of base64 images. You've built Litmus in a single API call.

### 6. Competitive Intelligence War Room with Geographic Price Views

Price intelligence typically means scraping a competitor's page from one location. But pricing varies dramatically by geography, device type, logged-in state, and even time of day.

**How it works technically:** Fire parallel requests to `/scrape` or BrowserQL with different `proxyCountry` and `proxyCity` parameters for each request. The same product URL, queried simultaneously from Chicago, London, Tokyo, and São Paulo, often returns **different prices, different availability, and different promotional offers**.

**The non-obvious insight:** Use `/unblock` with `browserWSEndpoint: true` to bypass anti-bot protection, then reconnect with Playwright to execute a complex multi-page flow — like adding items to a cart to see the real checkout price. The **session persistence** feature means you can maintain a "shopper profile" across multiple scraping runs, building up cookies and browsing history that make your bot indistinguishable from a returning customer.

### 7. Lighthouse-as-a-Microservice: Continuous Accessibility and SEO Auditing

The `/performance` endpoint runs full Google Lighthouse audits and returns structured JSON — accessibility scores, SEO violations, Core Web Vitals, best practices — all via a single POST request.

**How it works technically:**

```json
POST /performance
{
  "url": "https://yoursite.com/page",
  "config": {
    "extends": "lighthouse:default",
    "onlyCategories": ["accessibility", "seo"]
  }
}
```

Returns a 350KB–800KB JSON report with every Lighthouse metric.

**The creative application:** Build an **accessibility compliance dashboard** that runs nightly, tracks WCAG scores per page over time, and automatically files Jira tickets when scores drop below thresholds. The data is structured enough to power automated regression alerts in CI/CD — fail the deploy if any page's accessibility score drops below 90.

### 8. Human-in-the-Loop Fraud Review with LiveURL Streaming

Browserless's **LiveURL** feature generates a shareable URL that streams a live headless browser session to any web browser — enabling a human to see, click, type, and interact in real-time while an automation script orchestrates the flow.

**How it works technically:** A Puppeteer script connects via WebSocket, navigates through a checkout or account creation flow, then calls the custom CDP command `Browserless.liveURL` to generate a shareable link. A fraud analyst opens this link, reviews the transaction details, and either approves or flags it. When the analyst closes the page, the `Browserless.liveComplete` event fires, and the script continues based on the decision.

**Why this is genuinely novel:** This creates a **hybrid bot-human workflow** where automation handles the 95% of routine navigation and data entry, but a human handles the judgment calls. The `interactive: false` option enables read-only monitoring mode for supervisors. Combined with **screencast recording** (`record=true`), every session is automatically captured as a WebM video for audit trails.

### 9. Browser-as-a-Function: Serverless Puppeteer Without the Server

The `/function` endpoint lets you POST raw JavaScript (ESM module format) that receives a full Puppeteer `page` object, executes arbitrary browser automation, and returns any data type — JSON, images, PDFs, binary files.

**How it works technically:**

```javascript
// POST with Content-Type: application/javascript
export default async ({ page, context }) => {
  await page.goto(context.url);
  const data = await page.evaluate(() => {
    // Extract whatever you need
    return document.title;
  });
  return { data, type: "application/json" };
};
```

You can `import` any ESM module from HTTP URLs (e.g., `import { parse } from "https://esm.sh/node-html-parser"`).

**Creative applications this enables:**
- URL-to-structured-data microservice
- Webpage-to-markdown converter using Readability + Turndown
- Chart rendering service using D3 or Chart.js from raw data
- Stateless compute node where the "runtime" is a full browser environment

### 10. Load Testing with Real Browsers Instead of HTTP Hammers

Traditional load testing tools (k6, JMeter, Locust) send HTTP requests. But modern web apps do most of their heavy lifting client-side — JavaScript execution, API calls triggered by component mounting, WebSocket connections, service worker initialization. **Only a real browser exercises the full stack.**

**How it works technically:** Spin up browserless in Docker with `CONCURRENT=50`, then launch 50+ simultaneous Puppeteer connections via WebSocket. Each connection navigates your app, clicks through critical user flows, fills forms, triggers API calls — exactly as a real user would.

**What makes this different from Selenium Grid:** Browserless's built-in **queueing system** gracefully handles burst traffic — requests exceeding the concurrent limit queue automatically rather than failing. The `/performance` endpoint can run Lighthouse audits *during* load testing to measure how performance degrades under real concurrent browser sessions — something no HTTP-based load tester can do.

### 11. Chrome Extension Testing in Headless CI Pipelines

Chrome extensions are notoriously hard to test in CI/CD because they need a real browser with extension loading capabilities. Browserless **supports loading custom Chrome extensions into headless sessions**.

**How it works technically:** Pass your unpacked extension directory via Chrome launch arguments:
```
--load-extension=/path/to/extension
--disable-extensions-except=/path/to/extension
```

Connect via Puppeteer or Playwright, navigate to pages where your extension should activate, and assert on the DOM changes or network requests your extension makes. Background scripts execute normally; content scripts inject as expected.

**The advanced pattern:** Test your extension against **dozens of target websites simultaneously** using parallel browserless sessions. Verify that your ad blocker actually blocks ads on the top 100 websites. Use `/screenshot` to capture before/after states showing the extension's visual impact.

## The Unusual Features That Make All of This Work

Several browserless capabilities appear mundane in isolation but become powerful enablers when combined creatively:

**Request interceptor** — lets you modify any network request mid-flight: inject authentication headers, swap API endpoints, or return mock responses. Turns the browser into a **programmable HTTP proxy**.

**`bestAttempt` flag** — tells endpoints to return whatever they can even when errors occur. Critical for resilience in large-scale crawling.

**`waitForFunction`** — accepts arbitrary JavaScript predicates, meaning you can wait for complex application states (like "the React app has finished hydrating and the data grid has loaded all rows") rather than just DOM elements.

**Session reconnect pattern** — the sequence `/unblock` → get `browserWSEndpoint` → connect Puppeteer → automate → `Browserless.reconnect` → disconnect → reconnect later creates **persistent, stateful browser sessions** that survive across separate API calls. This enables multi-step workflows that span hours or days: log in on Monday, check a dashboard on Tuesday, download a report on Wednesday — all in the same browser session with the same cookies, without ever re-authenticating.
